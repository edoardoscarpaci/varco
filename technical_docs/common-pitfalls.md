# Common Pitfalls & How to Avoid Them

Traps that have actually bitten someone in this codebase — each row is a real defect
class, not a hypothetical. They are *cross-cutting coding-pattern* pitfalls: the kind
that recur in any new code touching the same primitive (a shared-instance resilience
object, a DI binding annotation, a Mongo exclusive-upper-bound query), regardless of
which feature you are building.

**Scope of this page** — three kinds of pitfall live in three different places:

| Kind | Lives in | Example |
|---|---|---|
| Cross-cutting coding pattern | **this page** | "a per-call `CircuitBreaker` never opens" |
| Feature-specific operational (wrong env var → wrong runtime behaviour) | that feature's `features/*.md` **Pitfalls** section | "`VARCO_MIGRATE_MODE=upgrade` in a multi-pod deployment" |
| Agent/contributor workflow rule | [CLAUDE.md](https://github.com/edoardoscarpaci/varco/blob/main/CLAUDE.md) | "never invoke linting via `uvx ruff`" |

When adding a row, prefer the narrowest home that fits. A pitfall that only makes
sense while using one feature belongs to that feature's doc.

---

| Pitfall | Symptom | Root Cause | Fix |
|---------|---------|-----------|-----|
| **Direct bus access in service** | Service holds `AbstractEventBus` and calls `bus.publish()` | Violates layer rule; bus is infra, not for app logic | Always inject `AbstractEventProducer`; it abstracts the bus |
| **NATS handler raises under `FIRE_FORGET`** | Message is acked and never retried despite `AT_LEAST_ONCE` | The exception never leaves `_dispatch` (`bus.py`'s `FIRE_FORGET` branch only logs), so `_on_message` sees a successful dispatch | Use `COLLECT_ALL` (the default) or `FAIL_FAST` if you want JetStream-level redelivery on handler failure (Plan 019 / RT2-B) |
| **Events published after commit** | Events silently lost when broker is unavailable | Post-commit publish has no rollback path | Use `OutboxRepository` + `OutboxRelay` within same transaction |
| **Subscription in `__init__`** | Service won't instantiate if broker is down; hard to test | Coupling service creation to bus state | Make it a `@Singleton` `EventConsumer` — `CoreModule.start()` auto-registers it after the bus has started (Plan 051 / DI-5); defer to a hand `register_to()` call only for non-DI consumers |
| **Per-call CircuitBreaker** | Circuit never opens, all requests fail after threshold | Instance never accumulates enough failures | Use shared `CircuitBreaker` per external dependency |
| **Mixin hook doesn't chain** | Later mixins in MRO never run | Hook returns value without calling `super()` | Always `return await super()._hook_name(...)` |
| **Instantiate InvalidationStrategy outside lifecycle** | Consumer crashes on `start()` or subscriptions leak | Strategy may spawn background tasks or hold subscriptions | Let `CacheBackend` create it; call `backend.start()` / `stop()` |
| **Cache key collision** | Wrong data returned to different users | Key function doesn't include scope (tenant_id, user_id) | Use namespaced keys: `f"user:{tenant_id}:{user_id}"` |
| **Consumer never registered** | Events never delivered | The consumer is not a DI-bound `@Singleton` (or sets `auto_register = False`), so nothing calls `register_to()` | Make it a `@Singleton` in a scanned package (or `contribute(container, EventConsumer, obj)`) — `CoreModule.start()` registers it after the bus starts (Plan 051). A non-DI consumer calls `register_to(bus)` itself, after the bus has started — never in `__init__` |
| **Async lock at module level** | `RuntimeError: no running event loop` | Locks created before event loop starts | Create locks lazily inside methods: `self._lock = self._lock or asyncio.Lock()` |
| **Missing `await` on async call** | Coroutine leaked, cleanup never runs | Easy to miss on unfamiliar APIs | IDE linting catches this; always `await` calls to `async def` |
| **Per-call Bulkhead** | Concurrency never limited, dependency can be overwhelmed | Instance has its own fresh semaphore each call | Shared `Bulkhead` per external dependency, same as `CircuitBreaker` |
| **InMemoryRateLimiter in multi-pod** | Each pod has its own counter; total rate = N × configured rate | Per-process storage, not shared | Use `varco_redis.RedisRateLimiter` for distributed (multi-pod) enforcement |
| **In-process `Bulkhead` in multi-pod** | Each pod caps its own concurrency; fleet-wide concurrency to the downstream dependency = N × `max_concurrent` | `varco_core.resilience.Bulkhead` is a per-process semaphore, not shared state — the same defect class as `InMemoryRateLimiter` above, but for *concurrency* rather than *rate* (U-7, Plan 005 Phase 8: they are genuinely different primitives) | Use `varco_redis.RedisBulkhead` — a Redis sorted-set-backed distributed semaphore with TTL-based reclaim for crashed holders (mirrors `RedisLock`'s Lua pattern); same `call()`/`protect()`/`available_slots()` surface as `Bulkhead` |
| **`InMemoryIdempotencyStore` in multi-pod** | A retried request routed to a different pod re-executes instead of replaying — a client sees no protection at all, silently | Same defect class as `InMemoryRateLimiter`/in-process `Bulkhead` above: reservations/records live in a per-process `dict`, invisible to any other process (Plan 029 / D1) | Use `RedisIdempotencyStore`, `SAIdempotencyStore`, or `BeanieIdempotencyStore` for any multi-process deployment — see `technical_docs/features/idempotency-key.md` |
| **Hedging non-idempotent writes** | Duplicate side-effects (email sent twice, double charge) | Both hedged copies execute concurrently | Only apply `@hedge` to idempotent reads/upserts; never to INSERT or transactional writes |
| **`@Singleton` on pydantic `BaseSettings`** | `LookupError: Cannot resolve 'values'` at resolution — on providify < 1.1.0 | providify injects pydantic's `**values` ctor param | Register settings via a `@Provider` (see `varco_casbin.di`), not `@Singleton`. **Version nuance (Plan 014):** on providify ≥ 1.1.0 the per-parameter resolver skips `VAR_KEYWORD` params outright (`providify/_annotations.py:583-590`), so `@Singleton` on this exact shape now *appears* to work — `container.get(SomeSettings)` resolves and is a singleton, and a required field raises `pydantic.ValidationError`, not `LookupError` (characterized in `varco_kafka/tests/test_kafka_di.py::TestKafkaRequiredFieldCharacterization`). The rule is still enforced regardless: the sanctioned shape must not depend on an undocumented third-party implementation detail that a future providify release could revert. `KafkaEventBusSettings`/`NatsEventBusSettings`/`RedisEventBusSettings` were converted to `@Provider` factories (`kafka_event_bus_settings`/`nats_event_bus_settings`/`redis_event_bus_settings`) for exactly this reason — see `plans/014-refactor-di-settings-and-provider-helper.md` |
| **Quoted `@Provider` return annotation** | An *unrelated* provider fails with `TypeError: xxx() missing 1 required positional argument`; every `Inject[...]` in the container is silently dropped | Under PEP 563 `-> "Foo"` is stored as the string `"'Foo'"`; providify's fallback `eval` returns the **str** `'Foo'` and registers it as the binding interface → `DIContainer._build_localns()` raises `AttributeError: 'str' object has no attribute '__name__'` → `_collect_kwargs_sync()` swallows it with `hints = {}` for **every** provider | Never quote a `@Provider` return annotation (`from __future__ import annotations` already makes it lazy) and import the type at **module scope** so `fn.__globals__` can resolve it. Guarded by `varco_fastapi/tests/test_di_binding_health.py` |
| **Quoted `TypeAlias` used in an injected annotation** | `AnnotationResolutionError: … TypeError: unsupported operand type(s) for \|: 'str' and 'NoneType'` at `validate_bindings()` (providify ≥ 1.1.0), or the parameter is **silently never injected** (< 1.1.0) | `X: TypeAlias = "Foo[Bar]"` binds the **string** to the module name at runtime, so any annotation doing `X \| None` evaluates `str \| None`. Quoting is usually a symptom of the inner type being imported under `TYPE_CHECKING` | Prefer annotating the **interface directly** (`Serializer[Event]`, not an alias). If you must alias, import the referenced types at **runtime** and leave it unquoted, or use PEP 695 `TypeAliasType`. Guarded by `varco_core/tests/test_event_serializer_alias.py` |
| **Protocol impl not resolvable by DI** | `container.get(Serializer[Event])` finds no binding although a conforming class exists | Structural (`Protocol`) satisfaction is invisible to the container — it binds on declared base classes | Subclass the protocol **explicitly** (`class JsonEventSerializer(Serializer[Event])`) and decorate it; use `@Fallback @Singleton` for a framework default so any app binding wins regardless of registration order (Plan 045; see `technical_docs/features/dependency-injection.md`) |
| **A package's suite is green but its container won't bootstrap** | Tests pass; a real app dies at startup with `AnnotationResolutionError` (or a cycle/scope-leak that only surfaces once every binding is wired together) | No test hit a path that resolves *binding* annotations — unit tests construct objects directly instead of resolving them | Add a `container.scan(pkg); container.validate_bindings()` test per package — one call covers every present and future singleton's annotations (see `varco_redis/tests/test_redis_di.py`) **plus** `container.validate(raise_on_error=False)` filtered to structural errors only (`AMBIGUOUS_BINDING`/`CIRCULAR_DEPENDENCY`/`SCOPE_LEAK`/`LIVE_REQUIRED`/`UNRESOLVED_ANNOTATION`, tolerating `MISSING_BINDING` since a package scanned alone legitimately lacks the app's own bindings) — providify ≥ 2.0.0, via the shared `testkit/varco_conformance.providify_health.assert_no_structural_di_issues()` helper (Plan 016 / RL-3a) |
| **`container.provide(lambda: X())`** | `ProviderBindingNotDecoratedError` at bootstrap | `provide()` only accepts `@Provider`-decorated callables and takes no second "interface" argument | Declare a module-level `@Provider(singleton=True) def x() -> X:` and pass the function |
| **Override registered after `install()`/`scan()`** | ⚠️ Historical (pre-3.2.0/Plan 045) — every varco framework default is now `@Fallback`, so this no longer happens: an application binding wins regardless of registration order | Was: equal-priority bindings resolved to the **first** registered | Register your override in **any order** — see `technical_docs/features/dependency-injection.md` |
| **Marked a `HealthCheck` (or any `get_all()`-consumed contribution) `@Fallback`** | It vanishes from the collection the moment the app adds its own check | A `@Fallback` binding is excluded from `get_all()`/`aget_all()`/`list[T]` the instant any non-fallback sibling exists — a collection contribution is designed to always be present alongside an app's own | Never mark a collection contribution `@Fallback` — a plain qualified `@Singleton` is correct (Plan 045; see `technical_docs/features/dependency-injection.md`) |
| **Per-call `Singleflight`** | Concurrent misses never coalesce — the loader runs once per caller, same as before | A fresh `Singleflight()` has an empty in-flight dict every call — same defect class as a per-call `CircuitBreaker`/`Bulkhead` | `@cached` creates one `Singleflight` per decorated function at decoration time; `CacheServiceMixin` creates one per service instance (lazily, on first use) — never construct one inside a request handler |
| **Coalescing on a pre-tenant-namespaced key** | Cross-tenant data leak — two tenants' concurrent misses share one recompute and one result | `Singleflight`/`read_through()` never build or namespace keys themselves; a caller that coalesces on the raw pk instead of the final `tenant:{id}:`-prefixed key defeats tenant isolation | Always pass the final, already-namespaced cache key (the one `tenancy_cache_key()`/`CacheServiceMixin._cache_key()` produced) to `Singleflight.do()`/`read_through()` — guarded by `varco_core/tests/test_cache_singleflight_tenancy.py` |
| **Per-call `RedisPubSubBackplane`** | Invalidations never propagate — each instance has its own listener/subscription state | Same shared-instance rule as `CircuitBreaker`/`Bulkhead`/`Singleflight` | Construct one `RedisPubSubBackplane` and pass it into every `LayeredCache` that must share coherence; let `LayeredCache.start()`/`stop()` drive its lifecycle, never call `start()`/`stop()` directly |
| **Adding a bulk method directly to `AsyncCache`** | `isinstance(third_party_cache, AsyncCache)` silently starts returning `False` for out-of-tree caches | `AsyncCache` is `runtime_checkable` — `isinstance()` tests method presence, so any new method changes what satisfies it | Add to `BulkCache` instead (Plan 011 / D-11) — `AsyncCache` stays byte-for-byte unchanged |
| **Forgot `<pkg>.bootstrap(container)`** | App starts, `AbstractEventBus` silently absent | ⚠️ Historical (pre-3.3.0/Plan 049) — `_try_resolve_component()`/`_collect_lifecycle_components()` used to auto-discover lifecycle components by scanning the container, swallowing every skip into `except Exception: pass`; Plan 049 deleted both, along with the `VARCO_LIFECYCLE_DISCOVERY_WARN` kill switch it grew in between. There is no more discovery to warn about | Since Plan 049, the module *is* the bootstrap: `CoreModule.start()` starts whatever `AbstractEventBus`/`AbstractJobRunner` resolves, `WsModule.start()` does the same for the two push adapters — a missing bus is a missing module in `create_varco_app(modules=[...])`, not a silent skip. See `technical_docs/features/dependency-injection.md`'s §Modules |
| **Decorated a `VarcoModule` subclass with `@Configuration`/`@Singleton`/`@Provider`** | The module is silently activated (`_register()` never runs; the class shows up as an ordinary DI binding instead) the moment its package is scanned — `container.scan("varco_core", recursive=True)` is `varco_core.di.bootstrap()` itself | `VarcoModule` is a plain class by design (Plan 049 / DI-1, §D-shape) precisely so the scanner never sees it; adding any providify marker defeats that and reintroduces the "scan silently activates a module" failure mode `container.scan()` scanning has for every `@Configuration` | Never decorate a `VarcoModule` subclass — construct it and pass the instance to `create_varco_app(modules=[...])`. Mechanically enforced by `test_modules_never_scanned.py` (`varco_core` + `varco_fastapi`) |
| **App works, but every request is anonymous** | `RequestContextMiddleware` populates `AuthContext`/`current_tenant()` on every request, but every one comes back with an anonymous, unauthenticated subject — no exception, no obvious log line | Never bound an `AbstractServerAuth` in the container. `FastAPIModule` contributes `RequestContextMiddleware` **unconditionally** (Plan 049, pre-049 parity) — with `AbstractServerAuth` resolvable it runs the real auth strategy, with nothing bound it still runs in anonymous mode (`server_auth or AnonymousAuth()`) rather than being omitted | Bind a real `AbstractServerAuth` (e.g. `JwtBearerAuth`) before `create_varco_app()`. ⚠️ Neither `inspect_http_edge()` nor the security posture preflight reports this today — verified absent from both modules' `check=` id sets — so nothing surfaces the omission at startup; the only way to catch it right now is to notice the response itself (or a test asserting on the real subject) |
| **`varco_memcached.async_bootstrap()`/`varco_redis.di.async_bootstrap()` opens a pool you didn't want** | An unwanted connection is opened just from calling `async_bootstrap()` | Plan 046 removed `setup_cache=` from both — `async_bootstrap()` now *always* installs the connection-opening `@Configuration`; there is no scan-only path through it | Call plain `bootstrap(container)` for the sync-scan-only equivalent — it never opens a connection. `async_bootstrap()` means "and open the connection", unconditionally, on both backends now |
| **Expected a second `bind_x`/`enable_x` call to replace the first (Plan 046)** | `AlreadyBoundError` instead of the previous binding silently winning (or, pre-046, sometimes an opaque `AMBIGUOUS_BINDING` at resolution time) | providify's `container.provide()` always appends; a second call to `bind_trust_store`/`enable_feature_flags`/etc. now raises at the call site rather than registering a second, dead-weight competing binding | Qualify the second binding (`bind_websocket_adapter(container, qualifier="orders")`) to have two, or use providify's `di_overrides`/`ContainerOverrides` fixture in a test to replace one |
| **Linting with `uvx ruff`** (applies to `ruff check` AND `ruff format --check`, Plan 020 / RL-17) | Local green, CI red (or vice versa) with no code change | `uvx` resolves the newest ruff release at invocation time; CI resolves the pin recorded in `uv.lock` | Always `uv run ruff`, never `uvx ruff` — the pin lives in the root `[dependency-groups] lint` group (Plan 017 / RL-6) |
| **Assuming `f"{SomeVarcoEnum.MEMBER}"` still yields `ClassName.MEMBER`** | Log lines / f-strings involving `HealthStatus`, `CircuitState`, `ErrorPolicy`, `DispatchMode`, `PKStrategy`, `KafkaDeliverySemantics`, `NatsDeliverySemantics`, or `BackpressurePolicy` suddenly print the bare value instead of `ClassName.MEMBER` | Python 3.11 changed `Enum.__format__` to print `ClassName.MEMBER` for `(str, Enum)` mixins; Plan 020 / RL-15 migrated all eight of these to `enum.StrEnum`, which undoes that change and formats by value | Intended as of 3.0.0 (BREAKING, see CHANGELOG) — `.value`, `json.dumps(member)`, and pydantic `model_dump(mode="json")` are all unaffected either way; update any `str()`/`%s`-log-scraping regex that depended on the old `ClassName.MEMBER` text |
| **Restarting a session-scoped container** | Unrelated tests in the same package fail with connection errors after a chaos test runs | The session-scoped fixture (`redis_url`, `kafka_bootstrap`, …) is shared by the whole package suite — restarting/pausing it under one test breaks every other test mid-flight or afterward | Declare a **module-scoped `*_container_chaos` fixture inside the chaos module itself**, never in `conftest.py` (Plan 018 / RT7, §chaos-fixture) — see Test Conventions' "Chaos tests" paragraph |
| **Assuming a chaos container's URL is stable across `restart()`** | `ConnectionRefusedError` after `restart()` even though `wait_ready()` returned successfully | Docker re-allocates ephemeral host ports on restart **by design** (research 006 §A/§B/§F) — platform-independent, version-stable moby v1.3.0 → v29.1, including GitHub Actions' native-Linux dockerd. Not a WSL2-specific flake and not unverified — research 002 §1's original "port survives restart" claim is superseded (in-tree banner points here) | Fixed (Plan 019 / §RT7b-port, closes BACKLOG's RT7b-port-remap): read `chaos.url` at every use — it re-derives fresh from the docker daemon on every access, never memoised. Pin the host port when the server advertises its own mapped address at first boot (Kafka's `tc-start.sh` bakes `KAFKA_ADVERTISED_LISTENERS` in as a literal — re-querying alone cannot fix it, so `kafka_container_chaos` additionally pins via `testkit/varco_chaos/ports.py`'s `reserve_host_port()` + `with_bind_ports`); do not assume the pause-based tests (`test_redis_chaos.py`, `test_nats_health_chaos.py`) needed this — pausing never remaps a port |
| **An `older_than`/`completed_before`/`expires_before`-style exclusive-upper-bound cutoff on a Mongo-backed store** | A chunked sweep (`BeanieDeadLetterQueue.delete_where()`, `BeanieJobStore.delete_where()`) returns `0` and stops while an entry the store itself still reports as strictly older than the cutoff remains | BSON `UTCDateTime` is millisecond-precision and pymongo floors **both** the stored value and the query operand, so a raw `$lt` is evaluated as `stored_ms < floor_ms(cutoff)` — excluding every row sharing a millisecond with the cutoff | Fixed at the two shipped call sites via `varco_beanie._bson_time.ceil_to_bson_millisecond()`, applied only to the exclusive-upper-bound operand — never to a lower bound (`$gt`/`$gte`) or an inclusive upper bound (`$lte`), where pymongo's floor is already correct. Any new Mongo-backed exclusive-upper-bound query needs the same widening |
| **Hand-rolled mtime-dict directory watching** | A Kubernetes-mounted Secret/ConfigMap rotates (kubelet's `..data` symlink swap) but the watching code never notices | Snapshotting `{p: p.stat().st_mtime for p in dir.glob(...)}` and comparing dicts only catches a changed mtime on the **name actually enumerated** — kubelet swaps a symlink target, not the visible file's own mtime, and the historical example (`PemFolderSource._has_changes()`, `varco_core/varco_core/authority/sources/pem_folder.py`) is exactly this shape | Use `varco_core.watch` (`StatPollWatcher`/`WatchfilesWatcher`) instead — its fingerprint is `(st_mtime_ns, st_size, st_ino)` of the **resolved** path, which changes inode across a symlink swap even when the visible name and its own mtime do not (Plan 025 / T1, §D-T1-fingerprint) |
| **Reaching into `varco_core.__dict__["Name"]` or assuming a broken submodule fails at `import varco_core`** | `KeyError` on a name never yet accessed (previously always present after the eager import block ran); or an `ImportError` from a typo'd optional dependency now surfaces at first **attribute access** (`varco_core.SomeName`), not at the top-level `import varco_core` statement, making the traceback land further from its cause | `varco_core/varco_core/__init__.py` is PEP 562-lazy as of Plan 028/P1a — `_LAZY` maps each `__all__` name to its defining submodule and `__getattr__` imports it only on first access, caching the result in `globals()`. These are the two accepted, documented incompatibilities (see the module's `DESIGN:` block) | Never index `varco_core.__dict__` directly — use `getattr(varco_core, "Name")` or `from varco_core import Name`, both unaffected. `varco_core/tests/test_lazy_init.py` resolves every `__all__` name on every CI run specifically to catch a broken submodule early; a new top-level `import` in any `varco_core/__init__.py`-adjacent module should be checked with `scripts/import_budget.py` before assuming it is free |
| **Producing a bus or DLQ from a `@Provider` without declaring `serializer` on the provider method** | `bind_cloudevents_serializer(container, …)` (or any custom serializer binding) changes the wire bytes on some backends and silently not on others — no error anywhere, just the wrong format | providify injects only what a `@Provider` **method** declares. A scanned `@Singleton` bus gets every constructor parameter injected for free; a provider-produced one gets exactly the parameters written in the provider's own signature. `varco_redis`'s `RedisEventBusSelectorConfiguration.bus()` declared `settings` alone, so both Redis buses fell back to `JsonEventSerializer()` while Kafka/NATS honoured the binding. The same shape hit all five DLQ backends, which constructed `JsonEventSerializer()` as a literal in `__init__` | Declare `serializer: Annotated[Serializer[Event] \| None, InjectMeta(optional=True)] = None` on the provider method and forward it — and annotate with the **interface** `Serializer[Event]`, never the concrete `JsonEventSerializer`, or a correct binding is still the wrong declared type. Never fix a missing binding by decorating `varco_core/event/cloudevents.py`: a module-level `@Singleton`/`@Provider` there is auto-registered by `container.scan("varco_core", recursive=True)` and would change the wire format of every scanning app. `SADeadLetterQueue` (047 N1) and `OutboxRelay` (via `ReliabilityModule`, Plan 050 / DI-10) both now declare `serializer` on their own provider/factory; only the hand-constructed forms still need `serializer=` at the call site (Plan 030 / N2 — see `technical_docs/features/cloudevents-envelope.md`) |
| **`@PostConstruct` on a `start()` couples construction to lifecycle** (Plan 050 / §D-bus) | A Kafka/NATS bus resolved anywhere in the container — even by an unrelated service injecting `AbstractEventProducer` — used to start itself at that moment, before migrations/tenancy had necessarily run, at a moment no phase controlled | `@PostConstruct` fires at first providify resolution, not at any point the app chose; removed from both `KafkaEventBus.start()`/`NatsEventBus.start()` in 4.0 — only the `BUS` phase (`CoreModule`) or an explicit `await bus.start()` starts them now | Never add `@PostConstruct` back to a bus's (or any phase-owned object's) `start()` — declare a `phase`/`components()` on the owning `VarcoModule` instead; `publish()` before `start()` now raises `RuntimeError` rather than silently working or hanging |
| **Reading a Redis Streams entry by the literal field name `payload`** | An external tool/`XRANGE` script sees no body once a CloudEvents serializer is bound | `RedisStreamEventBus` writes the field named by the serializer's optional `stream_field` attribute — `"ce"` under `CloudEventsJsonSerializer` (varco's named, versioned single-field convention), `"payload"` otherwise. The bus itself reads **either** name so a mid-rollout stream still drains; an outside reader hard-coding one name does not | Read whichever of `payload`/`ce` is present, exactly as `varco_redis.streams._read_payload()` does. Never split the envelope into one field per CloudEvents attribute — spec-owned names would enter varco's own `XADD` field namespace |
| **A tenant read from a request without a signed binding is not a tenant** | A request routes into another tenant's data with no error at all | A bare header (`X-Tenant-Id`) or an unvalidated `Host` subdomain carries no auth binding — any client that can reach the service can claim any active tenant (`TenantTrust.LOW`, the ❌ LOWEST row of brief 006 §1's trust table) | Configure a `varco_core.tenancy.source.TenantSourceChain` with a signed-claim source (`JwtClaimTenantSource`, `TenantTrust.HIGHEST`) and let the cross-check reject a disagreeing weaker source, rather than trusting the header/subdomain alone — see `technical_docs/features/tenant-provenance.md` (Plan 033 / S6) |
| **Bootstrapping a backend package expecting it to become live** (Plan 047) | `varco_kafka.di.bootstrap(container)` runs cleanly, but `get(AbstractEventBus)` still returns `InMemoryEventBus` | Bootstrapping a package only registers its bindings — since Plan 047, every one of the six selectable seams (`cache`, `dlq`, `idempotency`, `job_store`, `event_bus`, `revocation`) additionally gates its backend bindings on `@Requires(env="VARCO_<SEAM>_BACKEND", value="<name>")`. Scanning/installing a backend module no longer makes it the live implementation | Set `VARCO_<SEAM>_BACKEND=<name>` for every seam the bootstrapped package should serve (e.g. `VARCO_EVENT_BUS_BACKEND=kafka`) — see `technical_docs/features/dependency-injection.md`'s "Selecting a backend" section. `check_backend_selection()` also logs one `WARNING` naming exactly this situation ("bootstrapped but unselected") |
| **`VARCO_<SEAM>_BACKEND` value with the wrong case** (e.g. `Redis` instead of `redis`) | The named backend never activates — no error at bootstrap, just the in-process default serving silently, unless `check_backend_selection()`/`create_varco_app()` is called | providify's `@Requires(env=, value=)` match is exact and case-sensitive (`RequiresMarker.is_satisfied()`) — `"Redis" != "redis"` is simply a different, unregistered value, not a normalisation-pending one | Values are exact and lower-case, always (`[a-z][a-z0-9-]*`) — `check_backend_selection(container)` raises `BackendSelectionError` naming the known values for a seam whenever a named value doesn't match any of them, including a case mismatch |
| **`@Singleton` on a settings class ("providify cannot inject `**values`")** | Assumed this was the reason for the no-`@Singleton`-on-`BaseSettings` rule; the actual trap is different and this framing hid it | providify's `resolve_params()` skips `VAR_POSITIONAL`/`VAR_KEYWORD` outright (`_annotations.py:574-578`), so `**values` was never the problem. `pydantic_settings.BaseSettings.__init__` declares 29 *named*, annotated, defaulted keyword parameters (`_env_prefix`, `_env_file`, …) — an unresolved one is silently left to its default only if nothing else in the container happens to satisfy its type (`container.py:3753-3759`), so a class binding's configuration could silently depend on whatever else is bound | Register every settings class via `varco_core.settings.bind_settings()` (Plan 048 / DI-6) — a zero-argument `@Provider` closure has no parameters for the resolver to see at all |
| **A bare `REDIS_URL`/`POSTGRES_HOST`/`KAFKA_BOOTSTRAP_SERVERS`/`NATS_SERVERS` in a dev shell** | An unrelated env var silently changes which database/broker an app or test connects to | The `ConnectionSettings` family (§D-connection, Plan 048) deliberately keeps the third-party service's own env-var names, unprefixed by `VARCO_` — unlike every `bind_settings()`-registered class, these are never namespaced and never DI-bound | Treat these four names as hazardous exactly like the test-fixture `VARCO_TEST_*_URL` contract does — unset them before running anything that should use its own default, and never assume `bind_settings()`'s fail-fast/provenance guarantees apply to them |
